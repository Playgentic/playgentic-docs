Architecture: the agent harness

The scaffold itself is agent-agnostic. The agents live in their own plugin, playgentic-agents, which ships to Claude Code, GitHub Copilot and Codex. --agents wires that plugin into your repo, the same way Playwright's init-agents does.

What --agents writes

$ npx playgentic init my-suite --agents claude,copilot,codex
$ npx playgentic agents claude          # add to an existing project
  • All harnesses: .playgentic/config.json sets the base branch, branch prefix, worktree policy and run command. An AGENTS.md block describes this suite's conventions (docstrings, step wiki, world fixture) so the agents follow them.
  • Claude Code: .claude/settings.json registers the marketplace and enables playgentic@playgentic. CLAUDE.md imports AGENTS.md. Each user installs the plugin once: accept the install prompt when trusting the folder, or run claude plugin install playgentic@playgentic --scope project.
  • GitHub Copilot: the same keys in .github/copilot/settings.json. Each user runs copilot plugin marketplace add playgentic/playgentic-agents and copilot plugin install playgentic@playgentic once.
  • Codex: .codex/config.toml registers the marketplace and enables the plugin for trusted projects. Each user runs codex plugin add playgentic@playgentic once.

The command prints the one-time install step for each harness you picked. Every write is a merge, so re-running is a no-op. Pin a release with --agents-ref <tag>.

The pipeline

Invoke the author-tests skill (/playgentic:author-tests in Claude Code) with --gen or --heal. It runs these steps:

  1. Cut a feature branch (a worktree only if you confirm parallel work).
  2. Learn the suite.
  3. Agree numbered acceptance criteria with you.
  4. Run a read-only explorer against the live app.
  5. Have builders write and run tests in your conventions.
  6. Have a read-only auditor check that each test genuinely verifies its criterion.
  7. Commit only test files.

Pipeline config

.playgentic/config.json controls branching and how tests run. --agents writes it with your current branch as the base and the playwright-bdd run command. Anything in CLAUDE.md, AGENTS.md or your project rules takes precedence over it.

{
  "preferredBaseBranch": "main",
  "branchPrefix": "test/",
  "worktrees": "ask",
  "runCommand": "npx bddgen && npx playwright test"
}
  • preferredBaseBranch: the branch feature branches are cut from.
  • branchPrefix: prefix for each run's feature branch.
  • worktrees: ask (confirm each run), always or never.
  • runCommand: how the suite runs. Args like --grep are appended.

Customising: conventions and extensions

The agents read your team's rules from .playgentic/wiki/ at runtime. These files live in your repo, not the plugin, so plugin updates never overwrite them. init seeds them once, and after that they're yours.

  • CONVENTIONS.md: coding style and testing expectations (locators, page objects, steps, test data, what good UI and API tests look like). Every agent gets it, and it takes precedence over their defaults.
  • extensions/author-tests.md: extra rules for the orchestrator skill.
  • extensions/{explorer,builder,auditor}.md: extra rules for each agent, appended to its prompt.
  • index.md, steps/<domain>.md and pages.md: generated by npm run wiki. The agents use this step and page-object index instead of grepping. npm run wiki only rewrites files carrying its marker, so it never touches your own files.
Extensions win, guardrails included Extension rules override the built-in instructions where they conflict. For example, a builder extension can allow waitForTimeout for one legacy widget.

All of these are optional. Outside a playgentic suite, the agents infer conventions from your code: they never assume docstrings, a step wiki or a generated report.

Staying current

Nothing is copied into your repo, so there's nothing to sync. The plugin updates through each harness's marketplace. See the playgentic-agents README for details.
