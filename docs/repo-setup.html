Architecture: repo setup

Beyond the tests, a scaffolded suite ships the guardrails that keep an agent-written codebase honest: pre-commit gates, linting/formatting and CI. It ships formatter-clean: a fresh scaffold passes its own format:check, lint, lint:steps and typecheck. Here's what each piece is and how it fits — all of it yours to edit.

What's in the repo

my-suite/
  .husky/
    pre-commit              # lint-staged, then step-docstring lint + typecheck
  .lintstagedrc.json       # prettier + eslint on staged files
  eslint.config.mjs        # flat-config eslint + typescript-eslint
  .prettierrc.json         # formatting rules
  .prettierignore
  .github/
    workflows/lint.yml       # prettier, eslint, step docstrings, typecheck
    workflows/playwright.yml # desktop + mobile suites against TARGET_URL

Pre-commit gates (husky + lint-staged)

The pre-commit hook is the local quality gate. It runs three checks in order:

  1. lint-staged: prettier and eslint --fix on the files you're committing.
  2. npm run lint:steps: the step-docstring gate.
  3. npm run typecheck: tsc --noEmit over the whole suite.

A commit with an undocumented step, a lint error or a type error is blocked before it lands, so the agents' output has to clear the same bar as hand-written code before it enters history.

Why this matters for agentic work The docstring gate is what keeps the step wiki accurate — and the wiki is what lets the orchestrator reuse steps instead of duplicating them. The pre-commit hook is load-bearing for the whole reuse-before-writing principle.

Linting & formatting

  • ESLint (eslint.config.mjs) — a flat config with typescript-eslint. Run it with npm run lint.
  • Prettier (.prettierrc.json) — npm run format to write, npm run format:check to verify (CI runs this).
  • TypeScript — npm run typecheck (tsc --noEmit); also runs in pre-commit.

The playwright-test MCP

The agents plugin bundles the playwright-test MCP server (via npx playwright run-test-mcp-server, using this suite's own Playwright). It's the only thing that drives a real browser, and only the explorer and builder agents use it. The suite itself (scaffolding, linting, tests) doesn't need it.

CI workflows

Two GitHub Actions workflows run on pushes to main and on every pull request. Both use the current Node LTS.

  • lint.yml: the same gates as pre-commit, run in CI. It runs prettier (format:check), eslint, the step-docstring lint and the typecheck.
  • playwright.yml: runs the desktop and mobile projects as a matrix against your app and uploads a playwright-report-<project> artifact for each one (kept 14 days). You can also trigger it by hand (workflow_dispatch).

Before the Playwright workflow can run, add the app URL as a repository secret under Settings → Secrets and variables → Actions:

  • TARGET_URL (required): the base URL of the app under test. The job fails with a clear error if it's missing.
  • STANDARD_USER / STANDARD_PASS (optional): passed through for steps that sign in, the same way .env feeds them locally.

The job runs with --pass-with-no-tests, so a device with no tagged scenarios yet doesn't fail. Retries are on (1) and slowMo is off in CI. Secret scanning, dependency updates and editor settings are left to you, so the template doesn't commit you to any particular vendor or editor.

It's all yours Everything on this page is ordinary project config the scaffold drops in once. Edit it freely: playgentic never rewrites it. (The agents are a plugin and live outside your repo.)
